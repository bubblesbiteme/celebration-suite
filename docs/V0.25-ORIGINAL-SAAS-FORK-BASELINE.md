# Celebration Suite v0.25.0 — Original SaaS Fork Baseline

## Why this release exists
Earlier Celebration Suite releases reimplemented Sage & Celebration workflows across separate SaaS pages and APIs. That introduced behavior drift and fragile client-side state assembly. v0.25 changes the architecture: the working Sage & Celebration Event Workspace is now the planner UI baseline, while tenant isolation, licensing and white-label data boundaries are adapted behind it.

## Direct-fork baseline
- `event-workspace.html` and `event.html` use the mature original Sage workspace interaction model.
- Dashboard event cards now open `/event-workspace.html?id=<event_id>`.
- The original workspace calls a single unified `/.netlify/functions/event-workspace` contract again.
- The compatibility backend aggregates tenant-safe Celebration Suite tables into the payload shape expected by the original workspace.
- Original action names are translated server-side into tenant-safe Celebration Suite services or persisted compatibility state.

## Compatibility routes
Added tenant-safe compatibility functions for original direct calls:
- `event-workspace.mjs`
- `appointment-scheduling.mjs`
- `guest-admin.mjs` (`bulkUpdate` compatibility for floor-plan seating sync)

Legacy page routes used by the original workspace are redirected to the current tenant-safe pages while preserving event context.

## Original workspace action coverage
The compatibility bridge handles all action names currently invoked by the original Event Workspace, including checklist, timeline, notes, budget, design board, floor plan uploads/layout storage, documents, questionnaires, approvals, change orders, inventory operations, staff/labor, vendor operations, vendor quotes/bookings/payments/compliance, referrals, automations, reminders, lifecycle actions, templates and guest campaigns.

## White-label adaptations
Seller-specific Sage & Celebration strings were removed from tenant-facing workspace calendar exports, sender defaults and filenames. The tenant business name is used where appropriate.

## Assets restored
The original mobile workspace stylesheet and app icons needed by the direct-fork workspace are included.

## Migration
No new database migration is required. v0.25 uses the existing tenant schema through migration 0022 and stores compatibility-only workspace state in `tenant_events.workspace_data` where a dedicated tenant table does not yet exist.

## Validation

## Scope note
This is the architectural baseline for direct-fork parity. The Event Workspace is the first major planner surface moved to the direct original model. Remaining standalone modules can now be converted to the same approach without rewriting the core workspace again.
